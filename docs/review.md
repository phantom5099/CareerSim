# 代码复核规则

本文件同时约束派发方（主智能体）与复核方（子智能体）。规范本身在根 `AGENTS.md` 与
目录级 `AGENTS.md`；本文件只规定「实现完成后如何独立复核」。

---

## 一、派发复核（主智能体）

### 1. 时机与主体

实现完成、验证通过之后，汇报之前。复核不得由实现者本人或同一上下文完成，必须交给
独立的复核子智能体。实现者不自行出具复核结论。

### 2. 派发提示词

提示词先声明双方角色，再给材料。开头必须写明类似内容：

> 你是负责复核代码的子智能体。你的任务是按 `docs/review.md` 复核本次改动，
> 只输出发现与证据，不修改源码、不执行 git 写操作、不新增依赖。

随后给出：

- 原始需求与验收点，保留原文，不改写成结论；
- 明确不做的部分与已知约束；
- 改动文件清单与最终 diff，或可复现 diff 的命令；
- 已执行的验证命令与结果；
- 相关调用方与上下游位置，只给定位，不给判断。

要求复核者直接读文件与调用链。只依据派发摘要下结论的复核无效。

### 3. 复核者约束

- 只读：不修改源码、不执行 git 写操作、不新增依赖。
- 可以运行格式检查、类型检查、测试等验证命令。
- 发现问题只报告，修复由主智能体处理；复核者不参与修复。

### 4. 处理报告

- 先判断两件事：该发现是否改变原需求行为？是否属于本次方案范围？
- 不改变原需求行为、且属于本轮范围的问题：直接修复，修完重新验证。
- 需要变更原需求行为的问题：不得直接修改。原需求行为包括接口语义、错误语义、
  事件格式、配置默认值与既有数据含义。整理为「问题—证据—可选方案—影响面」上报用户。
- 超出本次方案范围的发现：不直接修改，也不顺手重构；整理后上报用户并注明建议处理
  时机。
- 修复改变了行为或触及新路径：再派一次增量复核，范围限定为修复 diff。
- 对报告有异议：用代码与可复现路径核对，不以「我认为」驳回。

## 二、复核程序（子智能体）

### 1. 复述意图

用自己的话写清：本次要解决的问题、验收点、明确不做的部分。与需求或对话不一致时先
指出，不要用复核掩盖理解偏差。

### 2. 重读最终 diff

- 从最终文件重读，不凭记忆或派发摘要。
- 对每个改动点回答：谁调用它、失败时谁感知、删除它会破坏什么。
- 找出 diff 之外被牵动但未改的地方：调用方、测试、类型、配置、文档、迁移。

### 3. 追踪四条路径

沿实际调用链走一遍，而不是停在单个函数：

- 正常路径；
- 失败路径；
- 取消或超时路径；
- 边界输入路径。

重点确认失败分支是否真的被处理，而不是只被捕获；返回值与错误是否被上游使用。

### 4. 按领域逐项检查

只检查本次实现涉及的领域；未涉及的写「未涉及」，不硬凑。

#### 资源与生命周期

适用于连接池、HTTP 客户端、取消令牌、锁、后台任务、文件句柄。

- 每个获取点是否都有对应释放点？正常、异常、取消、超时四条路径都释放吗？
- 锁 guard 是否在所有返回路径上释放？持有锁时是否执行了模型或工具调用？
- `CancellationToken` 是否从入口传到模型与工具？取消后下层是否真的停止工作？
- `PgPool`、`reqwest::Client` 是否被重复创建或意外泄漏？
- 后台任务是否有终止条件？失败是否至少被记录？

#### 并发与共享状态

适用于回合互斥、事件追加、缓存、重试、并发请求。

- `try_lock` 与 `SessionBusy` 的语义是否保持？是否引入了等待或排队？
- `std::sync::Mutex` 是否只用于不跨 `.await` 的短临界区？跨 `.await` 是否使用
  `tokio::sync::Mutex`？
- `append` 的 CAS 是否原子？两个并发追加是否可能同时通过 `stage` / `last_seq` 检查？
- `seq` 是否连续唯一？`last_turn_id` 是否可能回退或被覆盖？
- 会话锁表是否只增不减？空闲条目是否会被回收？
- 重复执行、重试、重复投递是否产生重复事件或重复副作用？
- 异常时锁、标记、占位是否释放？崩溃后残留状态如何恢复或被识别？

#### 错误与契约

适用于错误类型、公开 API、事件语义、模型调用。

- 错误是否保留 `source` 链？是否在边界把 `sqlx` / SDK 错误映射为领域错误？
- `unwrap()` / `expect()` / `panic!()` 是否进入了生产路径？
- 公开 API 是否泄漏了 `sqlx`、`async_openai` 或 `store` 内部类型？
- `TurnEndReason` 是否用对？取消必须写 `Interrupted`，`max_steps` 必须写
  `MaxSteps`，不能用 `Error` 代替。
- 空响应、未知工具、参数校验失败是否都有明确终态？
- 配置错误信息是否只包含变量名与非法值，不包含密钥或连接串？

#### 持久化与数据一致性

适用于事件日志、事务、迁移、阶段推进。

- 事务边界是否正确？一次逻辑操作涉及多次写入时，中途失败会留下什么状态？
- `append` 是否在同一事务内完成行锁、CAS、插入、缓存字段更新与阶段更新？
- `load` 的完整性校验是否仍覆盖首事件、`last_seq`、`last_turn_id` 与折叠阶段？
- `stage_completed` 是否仍是批次的最后一个事件？`Review` 是否仍被拒绝推进？
- 半截回合修复是否仍在下一次 `start_turn` / `finish_stage` 触发？
- 迁移是否只增不改？旧数据是否仍能读取？事件版本变化是否被处理？
- 写入失败时内存视图是否与持久化状态分叉？后续读取以谁为准？

#### 测试

适用于新增或修改测试、测试替身、断言。

- 断言是否落在可观察行为上：返回值、事件序列、终态、副作用、错误类型？
- 成功、失败、取消/超时、边界输入是否至少各有一条？
- 是否依赖真实时间、随机、网络或数据库？失败能否稳定复现？
- 测试之间是否共享状态？执行顺序变化是否影响结果？
- 测试替身是否只替代外部依赖？`MemorySessionStore` / `MockLlmClient` 与真实实现
  语义是否一致？
- 如果实现回退到修改前，测试是否会失败？
- 是否新增了根 `AGENTS.md` §7 列出的 8 类无意义断言？

#### 一致性

同一种行为在仓库内只允许一种实现风格；同一类型操作出现两种写法即视为问题，即使当前
行为正确。检查同类操作的全部位置并横向比对：

- 配置读取与校验；
- 错误构造、映射与日志输出；
- 取消检查与终态收尾；
- 锁获取与释放；
- 事件追加与折叠；
- 前端端点绑定与 mock 实现。

外部契约强制不同形态时，在边界集中适配，不把差异扩散到多个调用点。

#### 安全与外部输入

适用于接收模型输出、工具参数、环境变量、日志。

- 哪些数据来自外部？进入内部前是否校验或规范化？
- 工具参数是否按不可信输入处理？未知工具与非法 JSON 是否安全失败？
- SQL 是否全部参数化？是否存在字符串拼接进入查询？
- 密钥、连接串、完整简历内容是否进入日志、错误信息或事件日志？
- 启动错误是否经过脱敏？
- 外部输入能否导致内存、连接或事件无界增长？是否有上限？

#### 前端契约

适用于 `frontend/` 改动。

- 页面与 store 是否只通过 `api/endpoints/` 访问数据？是否直接 import 了 `mock/`？
- 接口、mock 实现与调用方是否同步变更？
- 领域类型与 DTO 是否放在正确位置？是否重复定义？
- `vue-tsc --noEmit` 是否通过？
- 是否引入未确认的 lint、测试或依赖？

#### 规范一致性

- 改动是否违反根 `AGENTS.md` 或目录级 `AGENTS.md` 的硬性规则？
- 是否新增了未确认的依赖、工具、后台任务或测试？
- 是否制造了纯格式 diff、兼容层或「为将来预留」的抽象？

## 三、证据门槛

每条发现必须包含：

- 触发条件：什么输入、时序或状态会走到；
- 具体位置：哪个文件、哪个分支或语句；
- 后果：错误结果、泄漏、数据不一致、契约破坏等；
- 为何现有代码挡不住。

达不到以上四项的，降级为「待确认」或不写。

每条发现同时标注两项，供派发方分流：

- 范围：本次方案内 / 超出本次方案；
- 行为：不改变原需求行为 / 需要变更原需求行为。

---

## 四、输出

- 结论：通过 / 有风险 / 未验证。
- 发现列表按严重级别排序，每条给出证据、修复建议、范围与行为标注。
- 对需要变更原需求行为或超出方案范围的发现，单列一节，写清为什么不能就地修复。
- 明确写出未验证的部分及原因。
- 不写「整体看起来没问题」这类无信息量结论。

---

## 五、严重级别

- **阻断**：会产生错误结果、数据损坏、泄漏、越权，或使主路径不可用。
- **重要**：边界或失败路径缺失处理，条件满足时出错。
- **建议**：可读性、结构、重复，不影响当前行为。

---

## 六、常见误报来源

- 只看了新增代码，没看调用方。
- 把框架保证当成需要防御的场景，或把需要防御的场景当成框架保证。
- 用「测试通过」代替「行为正确」。
- 把猜测写成事实。
- 报告没有真实入口的链路，或为不存在的使用场景设计防护。
- 把设计记录里的「后续版本」当成当前需求缺口。
